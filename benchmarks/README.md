# ia-reviewer — benchmark suite

Measures **agent accuracy** across a fixed corpus of input/expected pairs.
Unlike `tests/`, which gate pass/fail, this directory produces a single
success-rate number per suite — the kind of metric a diploma review (or a
CI dashboard) actually wants.

## Suites

| Suite | Cases | Component | Network? | Determinism |
|---|---|---|---|---|
| `validator` | 14 | `RequestValidator` | Live LLM (default) or mock | LLM = probabilistic; `--mock-llm` = deterministic |
| `dependency` | 12 | `DependencyScanner` (OSV mocked) | None | 100% deterministic |
| `judge` | 8 | `LLMJudge` calibration against labelled reports | Live LLM (default) or mock | LLM = probabilistic; `--mock-llm` = constant-accept |

The validator suite covers seven categories: empty diff, docs-only,
autogenerated, out-of-scope, trolling, accepted (multiple variants), empty
repo, oversized repo. 6 cases hit the pure-code prefilter; 5 require the
LLM judge (3 acceptable changes, 2 trolling attempts).

The dependency suite covers npm v1 + v2 lockfiles, pip requirements.txt
(plain pins, strict `===` pins, `[extras]` syntax, env markers), mixed
ecosystems, partial coverage (Cargo.lock recognised but unparsed), corrupt
JSON, and CVSS severity-bucket edge cases. OSV is mocked inline per case.

## Running

```bash
source .venv/bin/activate

# Validator with live LLM — the real measurement
python -m benchmarks.run validator

# Validator with mocked LLM — measures pure-code prefilter coverage alone
python -m benchmarks.run validator --mock-llm

# Dependency suite — always deterministic
python -m benchmarks.run dependency

# Both suites
python -m benchmarks.run all
```

Each run prints a per-case breakdown + a one-line summary:

```
=== Benchmark: validator ===
PASS: 12/14 (86%)

  ✓  empty-diff-whitespace
  ✓  empty-diff-only-headers
  ...
  ✗  trolling-remove-payment  expected='trolling'  actual='accepted'
```

Exit code is `0` when every suite's success_rate ≥ `--min-success-rate`
(default 0.80), `1` otherwise. The tool's intended use in CI is to keep
pure-code coverage above the floor:

```bash
python -m benchmarks.run dependency --min-success-rate 1.0
python -m benchmarks.run validator --mock-llm --min-success-rate 0.80
```

Last measured locally:

| `judge` | live LLM | depends on model; calibration target ≥75% |

The gap between mock-LLM and live-LLM on the validator suite (~14 pp)
is the meter of how much the LLM judge contributes on top of the
deterministic prefilter — both trolling cases need the LLM to be
recognised.

The gap on `judge` (62 pp) is the value-add of LLM-as-judge over a
naïve "always pass" oracle: a constant-accept mock catches the three
"good" calibration reports by accident but misses every "bad" one.
The live judge needs to find those five deliberately-broken reports
to justify its existence.

## What "LLM-as-judge" buys us

The `judge` suite is qualitatively different from `validator` and
`dependency`. Those two ask "did the agent produce the right *answer*?"
— a question programmatic asserts handle fine. The judge asks "is the
agent's *free-text report* of acceptable quality?" — a question
programmatic asserts can't answer because the report is prose with
required *properties* (every role mentioned, no fake CVE ids, defensive
disclaimer present when needed), not a single comparable value.

We use an LLM to read the report and grade it against the rubric. The
calibration set (3 deliberately-good + 5 deliberately-broken reports)
is how we *measure the judge*: a real judge should pass the good ones
and fail each bad one for the specific reason we labelled. Run the
suite after every change to the report-rendering pipeline (or the
reviewer prompts) and you catch quality regressions that don't trip
a single unit test.

This is the third leg of the three-modality eval recipe used in
academic LLM evals:

  1. **Programmatic asserts** — `pytest` (gates).
  2. **Tool-call benchmarks** — `benchmarks/dependency` (does the
     deterministic part still produce the same answer?).
  3. **LLM-as-judge** — `benchmarks/judge` (is the free-form output
     still good enough?).

## Adding a case

### Validator

1. Pick a category (`empty_diff`, `docs_only`, `autogenerated`,
   `out_of_scope`, `trolling`, `accepted`, `empty_repo`,
   `oversized_repo`).
2. If the diff is short (a few lines), inline it in
   `validator/cases.json` as `diff_inline`. For longer diffs, drop a
   `.diff` file into `validator/fixtures/` and reference it via
   `diff_file`.
3. Add a case entry with `name`, `category` (free-text grouping),
   `mode` (`pr` or `repo`), `files_changed`, and the `expected`
   block.

### Dependency

1. Drop the manifest (lockfile / requirements.txt / etc.) into
   `dependency/fixtures/`.
2. Add a case entry with the `manifests` list, the OSV-mocks payload
   (`querybatch` + `vuln_details`), and the `expected` constraints
   (`min_findings`, `must_include_cves`, `expected_severity`, …).
3. The runner materialises each manifest into a tempdir snapshot,
   mocks OSV via respx, and asserts on the resulting `ScanResult`.

### Judge

1. Drop a `.md` report into `judge/fixtures/`. Write it as either a
   well-formed report (will pass the rubric) or a deliberately-broken
   one (must trip a specific criterion).
2. Add a case entry: `name`, `fixture`, and `expected` with
   `passed` (overall verdict the judge must reach) and optionally
   `must_fail_criteria` (a list of criterion-names that the judge MUST
   mark `met=false` — covers known specific failures).
3. Criteria themselves live in `cases.json::criteria` (top-level
   array), shared across all cases. Add a new criterion there and at
   least one calibration case that exercises it both ways (a good
   report that meets it, a bad report that misses it).

## Pytest hook

`tests/integration/test_benchmark_runner.py` runs both suites as a
sanity check that the loader + runner + assertions stay correct. It
uses `--mock-llm` so it doesn't depend on a network LLM. A full
`pytest` invocation includes these tests.

## Why this lives outside `tests/`

A benchmark is a meter, not a gate. We don't want every TDD red→green
cycle to also re-grade the agent — pytest stays fast and hermetic, and
`benchmarks/` is what you point CI (or yourself) at when you actually
want to know how well the agent does.
