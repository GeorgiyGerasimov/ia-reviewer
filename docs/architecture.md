# Architecture

ia-reviewer is a LangGraph state machine that orchestrates three specialist
security reviewers in parallel, optionally pauses for a human, and publishes
a consolidated Markdown report. This document covers the graph topology,
the state model, and the agents.

## Graph topology

```
START
  │
  ▼
validate_request
  │   ├──→ notify_rejection ──→ END           (reject path)
  │   └──→ fan-out                            (accept path)
  ▼
[ dependency_review · injection_review · owasp_review ]   (parallel)
  │   fan-in
  ▼
review_decision                                          (Phase B)
  │   ├──→ [reviewers]   (rerun on human-approved clarification, cycle_count++)
  │   └──→ aggregate_results
  ▼
aggregate_results
  │
  ▼
publish_report                                           (report saved BEFORE any Q&A)
  │
  ▼
process_proposal                                         (Phase C — sequential loop)
  │   ├──→ process_proposal   (more pending findings, capped at MAX_EXPLOIT_PROPOSALS=3)
  │   └──→ END
```

**Why publish before process_proposal.** The exploit-proposal branch
asks the human approve/decline per finding via `interrupt()`. Without
a checkpointer those interrupts auto-skip; with one they can pause
the graph for a long time. Either way the user wants the consolidated
report saved to disk the moment aggregate finishes — not blocked on
"approve PoC for finding X?" Q&A. The proposals collected after publish
live in `state.exploit_proposals` (visible in chat / via `state`) but
intentionally **do not** make it into the on-disk markdown — that
would require a second publish step we deliberately omit, so the
report stays pinned to the moment aggregate produced it.

Wiring lives in [`src/graph/coordinator.py::build_review_graph`](../src/graph/coordinator.py).
The conditional routers are `route_after_validation`, `route_after_decision`,
and `route_after_proposal`.

### Why three reviewers in parallel

Each specialist has a focused prompt and a focused whitelist. Running them
sequentially would triple latency without improving recall. The `add`
reducer on `ReviewState.agent_reviews` makes the partial-state writes safe
under concurrent fan-out — each reviewer returns
`{"agent_reviews": [one_review]}` and LangGraph concatenates them.

### Why exploit proposal is sequential, not parallel

Phase C asks the human one question at a time via chat. Parallel
`Send`-style fanout would flood the chat with N concurrent "approve this
PoC?" prompts. The conditional self-loop is the trade-off: sequential UX
at the cost of repeated graph invocations.

## Run modes

The same graph handles both modes — the difference is in what
`validate_request` and the reviewers consume:

| Mode | Input to validator | Input to reviewers | Output |
|---|---|---|---|
| **PR** | `ReviewRequest.diff` (unified diff) | the diff (one LLM call total) | GitHub PR comment + on-disk `<thread_id>.md` |
| **Repo** | `ReviewRequest.repo_files` (file list from cloned snapshot) | per-file content from snapshot (one LLM call per file matching the reviewer's `PATH_PATTERNS`) | on-disk `<thread_id>.md` only |

`ReviewRequest.mode` is `"pr"` or `"repo"`. `BaseReviewer.run` branches on
this; PR-mode calls `_run_pr` (single LLM call against the diff),
repo-mode calls `_run_repo` (per-file iteration via the snapshot dir).

## State model

Defined in [`src/graph/state.py`](../src/graph/state.py).

```python
@dataclass
class ReviewState:
    request: ReviewRequest | None
    thread_id: str                          # stamped before astream; used by publish for filename
    validation: ValidationVerdict | None    # set by validate_request
    agent_reviews: Annotated[list[AgentReview], add]   # parallel-safe via `add` reducer
    cycle_count: int                        # Phase B re-review counter
    extra_context: str                      # human clarification spliced into next pass
    last_human_answer: str
    exploit_proposals: Annotated[list[ExploitProposal], add]   # Phase C results
    final_report: str                       # rendered Markdown
    pr_comment_id: int | None               # set on PR-mode publish
    error: str
    completed: bool
```

`ReviewRequest` is a single dataclass with a `mode` discriminator (rather
than a Union); fields not used by a given mode stay at their dataclass
defaults. PR-mode populates `pr_url`/`diff`/`files_changed`; repo-mode
populates `repo_url`/`ref`/`snapshot_dir`/`repo_files`.

## Validator (Phase A)

Two-stage gate in front of the reviewer fan-out.

**Pure-code prefilter** (no LLM):
- PR-mode: `empty_diff`, `docs_only`, `autogenerated`, `out_of_scope` (oversized)
- Repo-mode: `empty_repo`, `oversized_repo` (length > `MAX_REPO_FILES_HARD=5000`)

**LLM judge** (PR-mode only — anything that survives the prefilter):
strict-JSON `{verdict, category, reason}`. Returns `accept` on parse
failure so model flakiness can't block legitimate reviews. The model
sees only the first 8000 chars of the diff.

`ValidationVerdict.accepted` drives the `route_after_validation` edge.
Categories are stable strings (`empty_diff`, `docs_only`, `trolling`,
`empty_repo`, `oversized_repo`, …) so `notify_rejection`'s templated
comment stays consistent.

## Review decision (Phase B)

Sits between the reviewer fan-in and `aggregate_results`. Catches the
"reviewer signaled a problem (`passed=False`) but produced no concrete
findings" case — the classic "I think something's off but can't pinpoint
it." On that signal it calls `interrupt()` with a `review_clarification`
question. The human's reply is parsed by `_parse_resume`:

- Text starting with `rerun` (case-insensitive) → approve a re-review.
  Anything after `rerun:` (or `rerun `) becomes `state.extra_context` and
  is spliced into the next reviewer pass.
- Anything else → proceed to aggregate.

Bounded by `MAX_CYCLES=3` — initial pass plus up to two human-approved
reruns. On the third entry `_needs_clarification` check is skipped, the
agent returns `{"extra_context": ""}` and routing falls through to
`aggregate_results`.

## Exploit proposal (Phase C)

Per critical/major finding, sequential per-graph-invocation iteration:

1. **Self-confidence check** — LLM rates 0–10 how confidently it could
   draft a reliable PoC + drafts a `proposal_text`.
2. **Below threshold** (5/10) → status `skipped_low_confidence`, **no
   human prompt**. Avoids bothering the operator with low-quality
   suggestions.
3. **Above threshold** → `interrupt()` with an `exploit_approval`
   question. `main.py` schedules a `EXPLOIT_TIMEOUT_SECONDS=60` task that
   auto-resumes with `decline <finding_id>` if the human stays silent.
4. **`approve <finding_id>`** → a second LLM call generates the
   artifact (PoC code, repro steps). Status `approved`, artifact populated.
5. **`decline <finding_id>` or unmatched text** → status `declined`.
6. **Timeout** → status `timeout_declined`.

`finding_id` is content-addressed (SHA256 of `role|file|line|issue`,
first 12 chars). Same finding across two runs gets the same id, so the
operator can `approve <id>` deterministically.

Bounded by `MAX_EXPLOIT_PROPOSALS=3`. Once three proposals (any status)
exist in `state.exploit_proposals`, every remaining pending finding is
batch-skipped in one invocation with status `skipped_cap_reached` — no
LLM call, no human prompt. Prevents runaway LLM spend on PRs with many
critical findings.

## Interrupts without a checkpointer

`interrupt()` requires a checkpointer to suspend the graph and resume
later. When `build_review_graph(checkpointer=None)`, both
`ReviewDecisionAgent` and `ExploitProposalAgent` are constructed with
`interrupts_enabled=False`:

- `ReviewDecisionAgent` skips the interrupt and falls through to
  `aggregate_results` — the rerun path is unavailable but the graph
  doesn't stall.
- `ExploitProposalAgent` marks every qualifying finding as
  `skipped_no_human` without LLM calls — the graph proceeds to
  `publish_report` and the report still saves.

Production wires `AsyncPostgresSaver` via
[`open_checkpointer(settings.DATABASE_URL)`](../src/utils/checkpointer.py)
when `DATABASE_URL` is set; otherwise it yields `None` and the
degraded-but-functional path above runs.

## Aggregation & publishing

`CoordinatorAgent.aggregate` renders a single Markdown report from the
deduplicated `state.agent_reviews` (last-write-wins per role across rerun
cycles), plus an "Exploit proposals" section when `state.exploit_proposals`
is non-empty (approved entries get their proposal + `<details>`-wrapped
artifact; declined/skipped/timeout entries appear in a compact "Not
generated" bullet list).

The header line carries the review target:

- Repo-mode: `**Repository:** https://github.com/owner/repo (ref \`main\`)`
- PR-mode: `**Pull request:** https://github.com/owner/repo/pull/42`

`CoordinatorAgent.publish` branches on `state.request.mode`:

- **Repo**: writes `<reports_dir>/<thread_id>.md` and is done.
- **PR**: mirrors the same `<thread_id>.md` to disk (so the UI report
  panel works the same in both modes) **and** posts the report as a
  top-level PR comment via the GitHub REST client.

`_write_repo_report` skips the disk write entirely if `state.thread_id`
is empty — preventing stray `unknown.md` artifacts when tests or
mis-wired callers reach the publish path without a stamped thread id.

## Persistence — `ReviewStore`

[`src/storage/review_store.py`](../src/storage/review_store.py) writes a
finalized review state into two Postgres tables. The schema lives in
[`db/init/03-reviews-schema.sql`](../db/init/03-reviews-schema.sql)
(replayed on first DB boot and idempotently by
`ReviewStore.ensure_schema` at app startup):

| Table | Purpose |
|---|---|
| `reviews` | One row per review (UPSERT by `thread_id`): mode, target URL, ref, author, validation verdict, overall severity, finding count, full Markdown body, timestamps. |
| `review_findings` | Normalised findings: `(role, file, line, category, severity, issue, raw)` with an `ON DELETE CASCADE` FK to `reviews`. Non-promoted finding fields are kept in `raw JSONB`. |

`main.py::_persist_review` is called from both `_run_review` and
`_run_repo_review` after the graph completes. To get a finalised state
without depending on the checkpointer, `_stream_graph_with_progress`
mirrors each LangGraph chunk into the local `ReviewState` via
`_merge_chunk_into_state`. The merge rules match LangGraph's:
`agent_reviews` / `exploit_proposals` use the `add` reducer
(concatenate), everything else is last-write-wins.

Persistence is a side effect: any DB error is logged and swallowed —
the Markdown report has already been written to `reports/<thread_id>.md`
by `publish`, so audit-store failure never breaks the primary deliverable.

When `DATABASE_URL` is empty, the lifespan sets
`app.state.review_store = None`. `GET /reviews` returns `[]` (200) and
`GET /reviews/<id>` returns 404 — the UI degrades, the app still runs.

## Progress streaming

`main.py::_stream_graph_with_progress` drives the graph via
`astream(mode="updates")`. For every node update yielded, it:

1. Classifies the status (`fired` / `empty` / `rejected`).
2. Appends the envelope to `ProgressStore` (so a late WS client can
   replay the workflow state on connect).
3. Broadcasts to live WebSocket subscribers.

For `validate_request` updates, the envelope additionally carries
`accepted: bool` — the UI uses it to resolve the accept/reject branch
immediately rather than waiting for `__done__`.

The `clone_repo` step is **not** a LangGraph node — it runs before the
graph and emits its own `{node:"clone_repo", status:"active"}` →
`status:"fired"` envelopes manually via `_emit_progress`.

After astream completes a terminal `{node:"__done__"}` envelope is
emitted so the UI can grey out any circle that never fired.
