# Troubleshooting

A field guide to the symptoms we've seen in real runs, in rough order
of frequency.

## Report not appearing in UI / `/reports/<tid>.md` returns 404

Either the graph never reached `publish_report`, or it reached it but
the write was skipped. The server log tells you which.

**Confirm publish was reached.** Look for:

```
publish() entered: mode=repo, thread_id='<uuid>', final_report_len=<n>
publish wrote report: /Users/.../reports/<uuid>.md (<n> bytes)
graph node publish_report done; update keys=['completed']
```

Three of the four expected log lines must be present (the
`graph node <name> done` traces are emitted by
`_stream_graph_with_progress`). If they're all there, the file is on
disk — the issue is in the UI (try `curl /reports/<tid>.md` to confirm).

**If `publish() entered` is missing**, the graph hit `interrupt()`
without a checkpointer. Common cause: a critical/major finding from a
reviewer triggers `ExploitProposalAgent`'s human-approval prompt, but
`DATABASE_URL=""` so LangGraph can't pause/resume. **Resolution**: the
agents auto-skip interrupts when no checkpointer is wired — make sure
you're running recent code with that behaviour
(see [architecture.md](architecture.md#interrupts-without-a-checkpointer)).
If you DO want interrupts, set `DATABASE_URL` to a real Postgres
connection string.

**If `publish() entered` is there but no `publish wrote report`**, look
for one of:

- `publish: state.final_report is empty` — `aggregate_results` didn't
  populate it. Check whether `aggregate_results done` appears in the
  trace above; if not, the graph is broken earlier.
- `publish: skipping disk write — state.thread_id is empty` — the
  thread id wasn't stamped on the state. Should never happen in normal
  flow; treat it as a bug and check the call site of `graph.astream`.
- `publish failed for ...` — exception during `write_text` or
  `post_pr_comment`. Read the exception text.

## "Cloning into ...: Remote branch HEAD not found"

`git clone` rejects `--branch=HEAD` (HEAD is a symbolic ref, not a real
branch name). Resolution: pass `ref="HEAD"` (the default) — `clone_repo`
drops `--branch` entirely in that case and lets git pick the repo's
default branch. If you've explicitly set `ref="HEAD"` and still see
this, you're on stale code.

## "git executable not found on PATH"

The `git` binary is required for repo-mode. The lifespan does not
verify this at startup — the failure surfaces on the first repo review.
Install git on the host (Docker images that don't ship git: `apk add
git` / `apt-get install -y git`).

## `unknown.md` keeps appearing in `reports/`

Used to happen when tests instantiated `CoordinatorAgent(github=...)`
without `reports_dir=tmp_path`, defaulting to the project's `reports/`
directory, and `state.thread_id` was empty. `_write_repo_report` has a
defensive skip on empty `thread_id` now, so this no longer leaks —
delete the stale file and confirm the tests aren't writing fresh ones
with `pytest -q && ls reports/`.

## "address already in use" on uvicorn start

Another uvicorn from a previous session is holding port 8000.

```bash
lsof -i :8000              # find PID
pkill -f "uvicorn main:app"
# or, less politely:
pgrep -f "uvicorn main:app" | xargs -r kill -9
```

uvicorn without `--reload` does NOT pick up code changes, so if you
edited Python files and re-ran tests pass but the live behaviour
hasn't changed, restart uvicorn.

## "Report not available" stuck in the UI panel

The JS panel retries on 404 with exponential backoff for ~9 seconds.
If the report appears AFTER that window, the panel shows the failure
message and won't refresh until you trigger a new review. This is by
design — `reportFetchedForThread` short-circuits repeated attempts.

If you see this with a working server-side write (the log shows
`publish wrote report`), the JS retry budget was just too short for
your LLM. Open `templates/index.html`, find the `delays` array in
`fetchAndRenderReport`, and bump the totals — or open
DevTools → Network and manually `GET /reports/<tid>.md` to see the
content.

## All three reviewers return `status:"empty"`

Scope filtering. If `scope` excludes a reviewer's role
(e.g. `scope=["dependency"]` excludes injection + owasp), those
reviewers' `run` method exits immediately via `_skip_for_scope` and
returns `{}`. `_classify_progress` maps an empty update to `empty`,
and the UI greys those circles. **This is correct behaviour**, not a
bug. If you expected all three to run, set `scope=[]` (or omit the
field).

## Validator rejected my PR / repo

`notify_rejection` posts a category-templated comment (PR-mode) or
writes one to `<reports_dir>/<thread_id>.md` (repo-mode). The category
explains it:

- `empty_diff` / `empty_repo` — nothing to review.
- `docs_only` — only `.md` / `.rst` etc. touched.
- `autogenerated` — all changed files match autogen patterns, or the
  diff contains `@generated` / `DO NOT EDIT`.
- `out_of_scope` — diff > 200_000 chars.
- `oversized_repo` — tree > 5000 files.
- `trolling` — the LLM judge decided the PR is junk.

Each category has a stable string and a templated rejection message;
they're rendered via `_REJECTION_TEMPLATES` in
[`coordinator.py`](../src/agents/coordinator.py). Reject categories
land in `state.validation.category` so you can grep the log to confirm.

## OWASP review takes 30+ seconds

The OWASP whitelist is the broadest (source + infra + config), so the
per-file count is highest. With `MAX_FILES_PER_AGENT=200` and a slow
LLM, this can add up. Mitigations:

- Use `scope=["dependency"]` if you only care about supply-chain.
- Lower `MAX_FILES_PER_AGENT` in `.env` for tighter feedback loops
  during development.
- Switch to a faster gateway model (`AI_GATEWAY_URL` →
  `gpt-4o-mini`-class).

## Gateway responses come back with `content: null`

Some local models (especially reasoning-style models like
`gpt-oss-20b`) put their full output in a `reasoning` field and leave
`content` as `null`. Our `_parse_response` would crash on `None.strip()`.
**Workaround**: use a different model on the gateway, or pin to a
non-reasoning model via `AI_GATEWAY_MODEL`. We don't yet have an
auto-fallback for this case.

## Tests pass locally, fail in CI / Docker

Most common cause: missing system git. Add it to the image:

```dockerfile
RUN apt-get update && apt-get install -y --no-install-recommends git \
    && rm -rf /var/lib/apt/lists/*
```

Second cause: `.env` not present. Some tests import from
`src.utils.config` which reads `.env` via pydantic-settings — but
`Settings(_env_file=None)` is used in the unit test for
`AI_GATEWAY_URL` default to bypass that. If you see a new failure
about a setting value, check that you didn't hard-code a path that's
sensitive to cwd.

## Langfuse traces aren't appearing

1. Confirm both keys are set: `LANGFUSE_PUBLIC_KEY` AND
   `LANGFUSE_SECRET_KEY`. One alone isn't enough.
2. Check the startup log: `Langfuse tracing enabled` vs
   `Langfuse tracing disabled (LANGFUSE_* keys not set)`. If you see
   the disabled message, the keys aren't being read — verify `.env` is
   in the cwd of uvicorn.
3. For self-hosted: wait ~30s after `docker compose --profile
   observability up` — Langfuse's first-boot seeding takes a moment.
   Then check `http://localhost:3000/api/public/health`.
4. For Langfuse Cloud: verify the keys are for the right project, and
   that you can `curl -H "Authorization: Basic $(echo -n
   <pk>:<sk> | base64)" https://cloud.langfuse.com/api/public/health`.

## I can't reproduce a bug the user is seeing

The single most common cause is a stale uvicorn process. Without
`--reload`, uvicorn does NOT pick up code changes. Confirm with
`pgrep -fl uvicorn`, kill it, restart.

Second-most-common cause: editing `templates/index.html` doesn't
require a restart (Jinja2Templates re-reads on each request), but the
browser caches aggressively. Hard-refresh (Cmd-Shift-R) or use
DevTools → Disable cache while open.
