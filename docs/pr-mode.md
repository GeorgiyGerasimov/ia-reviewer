# PR-mode review

This mode reviews a GitHub Pull Request's unified diff and posts a
top-level comment on the PR with the consolidated verdict. Use it for
the common day-to-day case: a teammate opened a PR, you want a security
sanity check.

## Flow

```
POST /review {pr_url, scope?}
            │
            ▼
       BackgroundTask
            │
            ▼
GitHubClient.fetch_pr  ── pulls /repos/<owner>/<repo>/pulls/<n>/files
            │
            ▼
ReviewRequest(mode="pr", diff=<unified>, files_changed=[...], author=...)
            │
            ▼
validate_request   (pure-code prefilter + LLM judge)
            │
            ▼
[ dependency · injection · owasp ]   (parallel, each gets the full diff)
            │
            ▼
review_decision → aggregate_results → format_report → publish_report
            │                                                     │
            │                                              GitHub PR comment
            │                                                     │
            │                                              reports/<thread_id>.md
```

## Per-reviewer behavior

Each reviewer gets the **full unified diff** plus metadata (PR URL,
author, files-changed list). One LLM call per reviewer per pass — much
cheaper than repo-mode's per-file iteration. Reviewers parse a fenced
JSON block from the response into an `AgentReview` (findings list,
summary, severity, passed flag). On JSON parse failure the entire
response text is folded into a single "raw" finding with severity `info`
— defensive default so a misbehaving model doesn't fail the run.

## Validation

PR-mode's `validate_request` runs the full two-stage gate:

**Stage 1 — pure code, no LLM:**

- `empty_diff` — diff has no `+`/`-` payload lines (only headers/context).
- `docs_only` — every changed file matches docs heuristics (`.md`,
  `.rst`, `.txt`, `.adoc`, `LICENSE`, `CHANGELOG`, `docs/`, …).
- `autogenerated` — every changed file matches an autogen pattern
  (`package-lock.json`, `yarn.lock`, `poetry.lock`, `Cargo.lock`,
  `go.sum`, `*.min.{js,css}`, `*.pb.go`, `_pb2.py`, `(dist|build|gen)/…`)
  **or** the diff contains an `@generated` / `DO NOT EDIT` marker.
- `out_of_scope` — diff is larger than `VALIDATOR_MAX_DIFF_CHARS=200_000`.

**Stage 2 — LLM judge** (only for diffs surviving stage 1):

Strict-JSON `{verdict, category, reason}` over the first 8000 chars of
the diff. Categories the judge can return: `accepted`, `trolling`,
`other`. On any parse failure → default-accept (we don't want flaky LLM
output to block legitimate review work).

## Publishing

`CoordinatorAgent.publish` in PR-mode does two things in sequence:

1. **Mirror to disk** — `<reports_dir>/<thread_id>.md`. Same file
   layout as repo-mode so the in-app UI report panel works for both.
2. **Post the PR comment** — top-level issue comment on the PR via
   `GitHubClient.post_pr_comment` (GitHub treats PR conversation
   comments as issue comments at the API level — that's the right
   primitive for a top-level verdict, distinct from inline review
   comments).

The mirror happens first so even if the GitHub post fails, the report
is still readable through `GET /reports/<thread_id>.md`. The returned
state update includes both `pr_comment_id` and `report_path`.

If the validator rejected the PR, `notify_rejection` runs instead of
`publish_report`. It posts a category-templated short notice to the PR
conversation (and writes the same notice to disk so the UI panel
matches).

## Auth

`GITHUB_TOKEN` is **required** for PR-mode (the GitHub REST API for
`/pulls/<n>` and `/issues/<n>/comments` rate-limits anonymous access
aggressively, and posting comments requires authentication regardless).
Set it in `.env`:

```
GITHUB_TOKEN=ghp_xxxxxxxxxxxxxxxxxxxxxxxx
```

The token needs `repo` scope (or `public_repo` if you only review
public-repo PRs). See
[GitHub's docs on token scopes](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens).

## When to prefer repo-mode

PR-mode reviews the **changes**, not the surrounding context. If you
need to evaluate whether the *whole* codebase has a security issue (an
unsafe pattern that's already present but the PR doesn't touch), use
[repo-mode](repo-mode.md). Repo-mode is also better suited to auditing
projects you don't have PR access to.
