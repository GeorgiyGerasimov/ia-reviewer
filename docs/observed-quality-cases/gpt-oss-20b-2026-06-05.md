## Failure-mode taxonomy

The misreads cluster into a few recognisable patterns. None of them are
"the model is dumb" — they're "the model is too small to hold the
context that would prevent the wrong inference":

### 1. Surface-pattern triggers, no context check

| Surface in the code | Model conclusion | Reality |
|---|---|---|
| `f""" INSERT ... VALUES ($1, $2) """` (Python f-string holding an SQL template) | "SQL injection — f-string!" | The `$N` placeholders are parameterised by `conn.execute(sql, *args)`. asyncpg's canonical safe pattern. |
| `subprocess.run([...], shell=False)` | "Command injection — subprocess with user input!" | Argv list passed; no shell parsing happens. |
| `reports_dir / f"{thread_id}.md"` | "Path traversal!" | Adjacent line: `resolved.is_relative_to(reports_dir.resolve())` guard. |
| "Markdown report" mentioned | "XSS! Unescaped HTML in output!" | Markdown is plaintext. The UI's HTML renderer is escape-first. |

The model reacts to **the visible token-level pattern** (`f-string`,
`subprocess`, `/`-concat) and stops there. It never reads the
surrounding lines that would invalidate the inference. This is the
defining failure mode of small models on long-context security
review.

### 2. Hallucinated files generated from training-data priors

10 findings reference files that don't exist in the repo:
`src/auth.py`, `src/server.py`, `src/updater.py`, `src/utils/session.py`,
`src/logger.py`, `src/main.py`. Each comes with a confident description
(MD5 password hashing, `random.randint` session tokens, HTTP-only
updater, CORS `*`, `debug=True`) — but these are **classic items from a
generic FastAPI security checklist** that the model emitted as if it
had read the codebase. It didn't; it pattern-matched on "this is a
Python web app, here's the boilerplate list of issues."

A larger model with stronger instruction-following would have either
(a) not fabricated these or (b) gone to look at the file and noticed it
doesn't exist.

### 3. Ignoring documented `out-of-scope` items as "findings"

5 findings report things the project **explicitly documents as
intentional choices** (`docs/security-checklist.md::Threat model: not
in scope`):

- "No per-user authentication" — internal-tool threat model.
- "No rate limiting" — handled by consumption caps, not per-IP.
- "No HTTPS / HSTS" — reverse proxy responsibility.
- "Dev defaults marked `🔐 REPLACE-BEFORE-PROD`" — listed individually
  in `docs/security-defaults.md`.

The model can't see (or doesn't read) the security-checklist.md.
Even if it did, it would have to reason "this is intentional, not a
finding" — which is a higher-level move than small models reliably
make.

### 4. The approved exploit is fabricated end-to-end

The single approved PoC (`9d2e89b2274f`) builds an in-memory sqlite
database, defines its **own** vulnerable `retrieve_similar` function
using f-string concatenation, runs an injection against that fake
function, and prints "look, two rows came back."

**The vulnerable function in the PoC is NOT the project's
`ReviewStore.retrieve_similar`.** The PoC demonstrates a generic SQL
injection on code the model invented. This is a critical failure of
the exploit branch: the human reviewer is supposed to see the
disclaimer + the proposal, decide if it's plausible against their
code, and approve. Here the human (us, on the chat button) approved
something that doesn't apply to the codebase.

This is the case the LLMJudge calibration set is designed for:
the `no_fake_cve_format` criterion + a new `exploit_targets_real_code`
criterion would have flagged this.

## What this tells us about model choice

`gpt-oss-20b` is **too small for the security-review role in ia-reviewer**.
The architecture and the guardrails work — caps fired, exploit
disclaimer surfaced, JSON output parsed cleanly, graph topology
behaved — but the **finding-level signal is unusable** without a
much heavier post-filter.

Two ways to mitigate this without changing the model:
1. **Wire the LLMJudge into production** (see
   [`../judge-in-production.md`](../judge-in-production.md)) and use
   the judge's pass/fail as a flag on each report. A report with
   judge `passed=false` gets a UI warning banner.
2. **Tighten the reviewer prompt** with explicit instructions like
   *"Do not report items already mentioned in
   `docs/security-checklist.md` as known/out-of-scope"* and
   *"Cite the exact code line you're claiming is vulnerable; if you
   can't, omit the finding."*

The right long-term answer is to use a more capable model for the
reviewer prompt (Sonnet 4.6+, or a comparable open-weights model
≥70B parameters with strong code-understanding training). For
defensive use, even running gpt-oss-20b twice and intersecting the
findings would cut the false-positive rate sharply.

## Reproducibility

```bash
# 1. Bring the stack up (uses the gateway from your local .env)
docker compose up -d

# 2. Trigger the review
curl -X POST http://localhost:8000/review \
  -H 'Content-Type: application/json' \
  -d '{"repo_url": "https://github.com/GeorgiyGerasimov/ia-reviewer", "ref": "HEAD"}'

# 3. Watch the resulting report file
ls -la reports/<thread_id>.md

# 4. (After judge CLI lands) score the report
python -m src.evals.judge_report <thread_id>
```

Live numbers vary per run because the model is non-deterministic
(no fixed seed). The signal-to-noise ratio should stay around 10–15%
unless the prompt or model changes.
